# Anthropic 如何使用 Claude Code 运行大规模代码迁移

代码迁移——将生产代码库移植到新语言的项目——直到最近还是多年工程。

在过去一个月，Anthropic 的开发者使用 Claude Fable 5、Claude Opus 4.8 和[动态工作流](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)迁移了 10 个代码包，包含数万到数十万行代码。本文将介绍两个案例和这些项目的最佳实践。

Bun 联合创始人、Anthropic 技术团队成员 Jarred Sumner 使用 Claude Code [将 Bun 从 Zig 迁移到 Rust](https://bun.com/blog/bun-in-rust)。不到两周内产出百万行代码，合并前 Bun 的全部现有测试套件在 CI 中 100% 通过。合并后出现 19 个回归，现已全部修复。Rust 版本于 6 月在 Claude Code 中发布。

Anthropic Labs 联合负责人 Mike Krieger 在一个周末将 Python 代码库迁移到 16.5 万行 TypeScript。包括数百个智能体、8 个阶段门控、3 轮对抗性评审，以及最终的一致性检查——对比每个命令的输出与 Python 原版。

Claude Code 的新能力改变了这些长期推迟项目的经济学。以下是我们现在使用的六步流程，源自这些迁移的经验。

核心洞察是：**你不修代码。你修产出代码的流程（循环）。**

## 什么是 AI 代码迁移？

AI 代码迁移使用 AI 智能体将生产代码库移植到新语言或框架。工程师不再手动翻译文件，而是编写迁移规则和验证循环；智能体随后翻译、编译和测试，直到新代码的行为与原版匹配——将多年项目压缩到几周。

## 何时以及为何迁移语言

在直接讲*如何*之前，值得讨论*何时*和*为何*，因为这些项目的假设已经演化。

团队启动迁移是因为初始构建与当前项目之间的环境变化。要么已知的权衡变得受限，要么出现了更好的方法，要么原始生态系统正在萎缩。

例如，Jarred 最初选择 Zig，因为它提供 C 级性能和极简主义，非常适合独立创始人"在 LLM 出现前于奥克兰狭小公寓中一年内编写 Bun"。这种简单性伴随着已知的权衡，[他在此详述](https://bun.com/blog/bun-in-rust#just-be-really-smart-and-don-t-make-mistakes)。

快进到 2026 年。Bun 的 CLI 每月下载量超过 1000 万，在 Claude Code 中被广泛使用。

就在上个季度，这些权衡还不足以证明冻结路线图并投入资源到多季度项目的合理性。迁移语言可以提供更小、更快、更安全的系统，但没人想为此付费。

软件工程师还必须应对这些曾经巨型项目固有的职业风险。你可能维护两个并行代码库几个季度甚至几年，如果最终结果是 90% 的一致性，你的麻烦比开始时更大。

现在，最坏情况是删除分支重试。

仍然需要合理的商业理由。虽然百万行迁移不再需要在四年项目中花费 300-400 万美元的工程资源，但执行仍需数万到数十万美元或更多。例如，Bun 迁移消耗了 59 亿 uncached 输入 tokens 和 6.9 亿输出 tokens——按 API 定价约 16.5 万美元。Mike 的迁移主体部分是 2700 万 tokens。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58f8844b99cec5d277a9ee_27e78c5a.png)

Jarred 的百万行 PR。

**然而，迁移理由不再需要存亡攸关。** 一年的内存 bug 补丁记录，或一个长期瓶颈，现在就能证明其合理性。

编译步骤是 Mike 项目的推动力。他团队工作的内部工具作为单个二进制文件交付给用户。使用 Python 工具链为每个平台生成该二进制文件大约需要 8 分钟，在构建矩阵中每次发布总共等待 30 分钟。迁移后，相同的编译现在只需约 2 秒，二进制启动速度快 6 倍，团队还能淘汰一条单独的部署流水线。

## 为什么 AI 改变了代码迁移的经济学

Claude Fable 5 是我们最强大、普遍可用的模型。Fable 和 Opus 4.8 特别擅长通过子智能体委派、指导和验证并行工作流，同时找到实现既定目标的多条路径。

大规模代码迁移对这些高级模型是特别有效的用例，因为：

- **工作是并行的**。工作可以跨数千个独立单元（如文件和 crate）执行，因此智能体可以同时工作，而非一个等另一个。
- **上下文清晰且全面**。旧代码是模型的极佳规范。它也是帮助构建翻译智能体指南的核心参考。
- **有内置裁判**。许多大型代码库包含测试套件，智能体可以用它验证工作。当验证客观时，智能体表现最佳，因为模型可以针对真实标准持续工作数天，无需人工仲裁质量。
- **队列自我编写**。当编译器或测试运行失败时，那就成为智能体要修复的下一项。
- **它们需要一致性和边缘情况处理**：流程构建使偏移无处藏身：评审者为每个发现引用规则，因此违规成为队列项而非悄然分歧。当智能体遇到边缘情况时，修复成为后续所有智能体遵循的规则。

正如下文所示，Mike 和 Jarred 都在迁移流程的关键步骤中使用了 Fable，特别是在**顾问模式**中使用多个模型类别来优化 token 消耗。

## 大规模代码迁移的六个步骤

*以下流程已泛化以适用于多种语言和场景。更多详情，请阅读* [*Jarred 的博客*](https://bun.com/blog/bun-in-rust)*。你也可以访问* [*迁移入门套件*](https://github.com/anthropics/code-migration-kit-with-claude-code)*。注：入门套件是上述流程的泛化模板——不是这些特定迁移运行的版本。*

### 前提条件

开始迁移项目前的前提是建立强大的裁判，否则你没有退出条件或成功衡量标准。

裁判必须能在平等条件下评估原始代码和目标代码。用原始语言编写的测试套件通常依赖目标代码中不存在的内部函数。

构建裁判：

- **分类现有测试**。使用 Claude 识别哪些测试可以用语言无关的格式（如 shell 脚本、HTTP 请求、二进制调用）表达。对于不能的，让 Claude 将其重写为语言无关的格式。
- **在两个代码库上运行真实代码以确认通过**。然后在故意破坏的代码上运行以确认失败——不能捕获破坏的裁判不是裁判。

Jarred 有用第三种语言（TypeScript）编写的大型测试套件，但大多数项目不会这样。对于他的 Python 到 TypeScript 迁移，Mike 创建了 7 个真实场景的一致性 harness，并将任何行为变化视为需要修复的 bug。

在进入各阶段之前，此图可能帮助你跟进。这主要遵循 Jarred 的方法论，在每个阶段都有评审和门控。Mike 遵循类似的整体结构使用类似的循环工作流，但他端到端运行整个迁移，根据结果修改规则和工作流，然后再次运行——每次丢弃输出，直到第三次运行。

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58f8854b99cec5d277aa48_e7dd47de.png)

### 步骤 1 — 创建规则手册、依赖映射和差距清单

第一步是构建规则手册——翻译智能体将遵循的指南。这是你迁移中最重要的文档。

从 Claude 开始，给它两种语言的小代码片段并要求它翻译。记录它做出的决策。这些决策成为规则草案。

关键决策包括：
- 命名约定（snake_case vs camelCase）
- 错误处理模式
- 内存管理方法
- 标准库等价物
- 惯用法映射

接下来，构建依赖映射。列出原始代码库中的每个外部依赖，并识别目标语言中的等价物。这通常是人工判断——Claude 可以建议候选，但你验证它们的成熟度、维护状况和 API 一致性。

最后，创建差距清单。扫描代码库寻找在目标语言中没有直接等价的模式（如 Python 的元类、Zig 的 comptime）。你要么找到变通方法，要么记录"需要重新设计"的区域。

这一步是人力密集型的。Mike 花了一个完整工作日。但它为后续的所有自动化建立了基础。

### 步骤 2 — 在小批量上测试循环

在翻译整个代码库之前，在 5-10 个代表性文件的小批量上运行循环。目标不是产出生产就绪的代码——是压力测试规则手册。

运行翻译循环。审查输出。每次智能体做出错误决策或不一致翻译时，更新规则手册中的相应规则。然后丢弃翻译文件。目标是完善规则，而非渐进进展。

### 步骤 3 — 翻译所有内容

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58fd9c8899de91189a89e0_ai-migation-step4-5-6.jpeg)

对于其余步骤，你运行相同的多智能体循环架构：实现、评审和修复。

你可以将实现者工作分配给较小模型，并让评审者使用较大模型。例如，Mike 在主迁移中分散 12 个子智能体时使用了 Claude Sonnet。

工作队列应该是机械化的。批处理脚本通过检查磁盘上是否存在翻译文件来决定什么完成了，然后将待处理文件切片成批次供实现者智能体处理。因为队列每次都从磁盘重建，迁移在构造上是可恢复的。

在此阶段，智能体可能对完成的工作量过于谨慎。修复可以是一个直接、强调性的提示指令，加上编译器将在下一步捕获错误的上下文。

翻译器无法自信执行的任何内容都用 `// TODO(port): <原因>` 标记，留待步骤 4 处理。从此刻起，待办列表自我编写：编译器枚举错误，冒烟测试发现崩溃，套件报告失败。

两个对抗性评审者使用单独的上下文评估实现者的工作，评审者之间的分歧交由第三个智能体处理。当评审者在多个文件中持续捕获相同错误时，修复不是按文件进行。你在规则手册中添加一句话并重新生成受影响的批次。规则手册在此步骤中持续增长；代码从不针对它进行手动修补。

此步骤的一个重要设计决策是编译器的位置。Mike 在每个循环内运行 TypeScript 编译器，因为它在几秒内检查一个单元。Jarred 完全禁止循环内的编译器并将其推迟到下一步，因为 cargo 需要几分钟。

在此步骤，大部分繁重工作已完成，[提示开始变短](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/prompts/04-translation-kickoff.md)。

### 步骤 4、5、6 — 编译、运行和匹配行为

![](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a58fd76153c143199b57e1b_ai-migration-step3.jpeg)

这三个步骤共享相同的循环架构，并且需要逐步减少人工判断，因此我们一起介绍它们。

例如，**步骤 4** 通常可能根据语言和迁移规模融入步骤 3。

根据编译步骤的规模和难度，智能体可能根本不运行此步骤。Jarred 使用编排脚本执行此步骤，该脚本在整个工作空间中调用一次编译器。"修复者智能体"然后通过对抗性评审并行处理错误列表。构建再次运行，循环往复。

审查错误列表有助于捕获可能需要调整的系统性问题。例如，Jarred 遇到数千个 Rust 模块错误，这些错误在修复 Zig 的惰性编译容忍的循环导入后浮现。他通过编码逻辑来分类哪些依赖要删除、移动或重构边界来修复循环。

**步骤 5** 也有类似编译器错误列表的机械真实来源：冒烟测试的崩溃。同样，循环修复是将问题分组到类别中，在这种情况下按根本原因分组，由对抗性子智能体评审。

**步骤 6** 和我们故事的结尾是比较两个代码库中程序的行为。

我们的文件现在已翻译、编译和冒烟测试。现在是时候对它们进行分片并运行测试套件（来自前提条件阶段）。用"修复者智能体"处理失败，这些智能体针对两个代码库审查失败的测试。对抗性评审者检查它们的修复。

此循环的下一阶段是[构建守护进程](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/scripts/build_daemon.sh)，这是唯一允许重建二进制文件的进程。修复者编写补丁；守护进程批量处理它们，重建一次，重新运行受影响的测试，并将结果反馈回来。这序列化了最昂贵的操作，而非让多个智能体独立触发它。

当相同失败在许多测试中重复时，修复向上游移动：你修改产生 bug 的规则，并仅重新生成该规则涉及的文件。

Mike 的方法在此很重要，因为许多开发者不会有完善或已移植的测试套件。Mike 让 Claude 创建了一个小脚本，针对新迁移和原始 Python 代码库运行 7 个真实场景，并对比结果。每个失败的场景都有自己的修复智能体，循环运行直到全部七个通过。

然后他更进一步。Claude 设计了自己的端到端测试套件并在夜间自主运行，修复破坏的内容并连续四晚重新运行。结果，它捕获了任何场景列表都无法预测的小问题。

教训是缺少测试套件不会阻碍此步骤。如果你不能继承裁判，让 Claude 构建一个。你的原始代码库无论如何都是真实标准。

## 代码迁移最佳实践

每次运行都教会我们之前没有的东西。可以肯定你的下一次迁移会教你本指南无法教的东西。但一些实践在每个项目中都站得住脚：

- **不要盲目遵循本指南。** 每次迁移都不同。将此作为起点，在承诺之前与 Claude 一起规划你的特定迁移。
- **不要专注于单个失败。** 单个失败是循环的工作。修复者智能体会消灭它们。你的注意力应放在模式上。
- **让评审对抗化，验证机械化。** 对抗性评审允许更长时间运行的任务，通常值得 token 消耗。让脚本——编译器、diff、测试套件——成为裁判。
- **不要对所有事都使用最大模型。** Token 支出集中在你的循环中，因此要刻意设计它们。较小模型很好地处理大量实现扇出；为评审者和编写其他智能体将遵循的规则保留最大模型。
- **前置人工时间。** 规则手册和压力测试最耗时。之后的一切主要是队列消耗。
- **让工作队列机械化且可恢复。** 完成应该意味着"输出文件存在于磁盘上"。

## 评审循环结果，而非代码

Jarred 的 Bun 迁移现已投产，尽管每次迁移都有权衡。例如，约 4% 的 Rust 代码位于"unsafe"块内，主要是 C/C++ 边界的单行指针操作。

但新代码库明显更好。团队工具能检测到的每个内存泄漏都已修复：2000 次重复构建的一个基准测试从 6745 MB 内存降至 609 MB。二进制文件在 Linux 和 Windows 上小 19%。跨语言优化使 HTTP 服务和真实工作负载（如 next build 和 tsc）快 2-5%。

考虑是否该重新计算你长期推迟的迁移。选择你一直容忍的代码库，问 Claude 迁移流程是什么样的。
